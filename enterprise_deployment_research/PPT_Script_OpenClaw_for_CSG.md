## 第 04 页｜Skill、MCP、Plugin 的关系（直接回答客户问题 1.1）

**页面标题（PPT 上显示）：**
> **三种扩展方式：Skill 是"剧本"，MCP 是"工具箱"，Plugin 是"器官移植"**

**页面视觉内容（三列说明卡片）：**

| 类型 | 类比 | 本质 | 适用场景 |
|------|------|------|---------|
| **Skill** | 剧本/SOP | 一段 Markdown 指令，告诉 Agent 怎么完成某类任务 | 定制化工作流，如"每日新闻推送"、"合同审查" |
| **MCP（Model Context Protocol）** | 工具箱 | 标准化协议，让 Agent 连接外部系统（数据库、API、文件系统） | 连接智搜、OA、GIS 等内部系统 |
| **Plugin** | 器官移植 | 扩展 Gateway 核心能力，如新增通道（钉钉）、新增模型 | 深度集成，改变系统行为 |

**照读脚本：**

> 客户问 OpenClaw 和 Skill、MCP 的关系，这里我直接讲清楚。OpenClaw 是"平台"，Skill 和 MCP 是"能力来源"。打个比方：OpenClaw 是一个厨师，Skill 是菜谱，MCP 是厨房里的各种炊具。菜谱告诉厨师怎么做这道菜，炊具决定厨师能用什么材料和方法。所以 Skill 的优势是**低门槛、快速定制**——一个懂业务的人，写一段 Markdown 就能定义一个新的工作流，不需要写代码。MCP 的优势是**标准化对接**——只要你的内部系统实现了 MCP Server，Agent 就能直接调用，不需要为每个系统写专属适配器。这对南网这种有大量内部系统的企业来说，意义非常大。

## 第 07 页｜内网部署的能力边界（直接回答客户问题 1.2）

**页面标题（PPT 上显示）：**
> **内网部署：能力不是被"阉割"，而是被"重新定义"**

**页面视觉内容（两列对比）：**

| 维度 | 外网 OpenClaw | 南网内网部署 |
|------|-------------|------------|
| **模型** | GPT-5、Claude 4 等国际模型 | 国产模型（通义、文心、混元）或私有部署模型 |
| **Skill 生态** | ClawHub 数千个公开 Skill | 需自建内部 Skill 库（但开发门槛低） |
| **联网搜索** | 实时搜索全网 | 仅限内部知识库（智搜、企业知识图谱） |
| **浏览器控制** | 可操作任意公网网站 | 可操作内网 Web 系统（OA、ERP、GIS 等） |
| **文件操作** | 本地文件系统 | 内网文件服务器、NAS |
| **IM 通道** | Telegram/WhatsApp | 钉钉/企业微信/内部 IM |
| **核心 Agent 能力** | ✅ 完整 | ✅ 完整（Agent Loop 不依赖外网） |

**照读脚本：**

> 客户问内网部署会"阉割"哪些能力，我的回答是：**Agent 的核心能力一点都不会少，只是能力的"输入源"和"操作对象"变了**。Agent Loop、任务规划、多步骤执行、工具调用——这些核心逻辑完全不依赖外网，在内网跑得一样好。变化的是两件事：第一，模型换成国产模型或私有部署模型；第二，Skill 里调用的外部服务，从公网 API 换成内网系统。所以更准确的说法是：内网部署不是能力缩水，而是把 OpenClaw 的"触手"从公网系统换成了南网的内部系统。这反而是一个优势——Agent 能直接操作你们的 OA、ERP、GIS，这是外网 OpenClaw 做不到的。

## 第 08 页｜内网 Skill 开发：以"AI 新闻推送"为例（直接回答客户问题 1.3）

**页面标题（PPT 上显示）：**
> **内网 Skill 开发不是从零开始，而是"换数据源"**

**页面视觉内容（流程对比图）：**

**外网版"每日 AI 新闻推送" Skill：**
```
定时触发 → 调用 Bing/Google 搜索 API → LLM 摘要 → 推送 Telegram
```

**内网版"每日 AI 新闻推送" Skill（南网）：**
```
定时触发 → 调用智搜 MCP Server → LLM 摘要 → 推送钉钉/企业微信
```

**需要额外开发的内容：**

| 开发项 | 难度 | 说明 |
|--------|------|------|
| 智搜 MCP Server | ★★☆ | 封装智搜 API 为标准 MCP 接口，约 200-300 行代码 |
| 钉钉 Channel Plugin | ★☆☆ | 已有官方模板，主要是配置工作 |
| 新闻推送 Skill 文件 | ★☆☆ | 一个 Markdown 文件，定义任务流程，无需编码 |

**照读脚本：**

> 客户举了一个很好的例子——"每天推送 AI 新闻"。在外网，这个 Skill 调用 Google 搜索 API，然后让 LLM 摘要，推送到 Telegram，大概 10 分钟就能配好。在内网，逻辑完全一样，只是把"Google 搜索"换成"智搜"，把"Telegram"换成"钉钉"。**Skill 本身的结构不需要重写，只需要换数据源**。额外需要开发的，主要是两件事：一是给智搜写一个 MCP Server，把智搜的搜索接口包装成 Agent 能直接调用的标准工具，这大概是 200-300 行代码的工作量；二是钉钉的通道配置，这个有官方模板，主要是配置工作。所以总体来说，内网 Skill 的开发成本比大家想象的要低很多，核心是先把内部系统的 MCP Server 建好，后面所有 Skill 都能复用这个基础设施。

## 第 09 页｜国产化路径：OpenClaw vs NanoClaw（直接回答客户问题 1.4）

**页面标题（PPT 上显示）：**
> **国产化不是"换一个 OpenClaw"，而是"在 OpenClaw 上换模型"**

**页面视觉内容（对比分析表）：**

| 维度 | OpenClaw（开源） | NanoClaw（港中文，闭源商业） |
|------|----------------|--------------------------|
| **开源程度** | 完全开源，可审计 | 闭源，代码不可见 |
| **二开难度** | 低，社区活跃，文档完善 | 高，依赖厂商支持，定制受限 |
| **Skill 生态** | 数千个开源 Skill，可直接复用 | 生态封闭，Skill 需从头开发 |
| **国产模型支持** | 原生支持通义、文心、混元、Kimi | 原生支持，但选择空间小 |
| **信创合规** | 需自行完成信创认证 | 厂商提供信创认证背书 |
| **长期维护** | 社区驱动，持续迭代 | 依赖厂商商业决策 |
| **推荐场景** | 有技术团队、需深度定制 | 无技术团队、需快速交付 |

**国产化的正确姿势（OpenClaw 路径）：**
- 模型层：替换为通义千问 / 文心一言 / 混元 / 私有部署模型
- 基础设施：部署在国产服务器 + 国产操作系统（麒麟/统信）
- 数据：全量留存在内网，不出域

**照读脚本：**

> 关于国产化，我想先纠正一个认知误区：**国产化的核心是"模型国产化"和"基础设施国产化"，而不是"换一个国产的 OpenClaw 替代品"**。OpenClaw 本身是开源的，代码可审计，可以部署在国产服务器和国产操作系统上，这本身就满足了大部分信创要求。模型层，OpenClaw 原生支持通义、文心、混元，切换非常简单，改一行配置就行。NanoClaw 的问题在于它是闭源的，代码不可见，生态封闭，二开困难，长期来看对南网这种有深度定制需求的客户来说，反而是更大的风险。当然，如果南网完全没有技术团队来维护，NanoClaw 的"开箱即用"确实有优势。但如果有技术团队，我们强烈建议走 OpenClaw 路径，因为生态、可控性、长期维护成本都更优。

## 第 10 页｜南网核心落地场景：三个最有价值的切入点

**页面标题（PPT 上显示）：**
> **南网场景下的三个"AI 调度员"落地方向**

**页面视觉内容（三个场景卡片）：**

**场景一：跨系统智能调度**
- 触发：运维人员在钉钉说"帮我查一下今天广州片区的告警，整理成报告"
- Agent 行为：调用告警系统 MCP → 调用 GIS MCP → LLM 分析 → 生成报告 → 推送钉钉
- 价值：原来需要 30 分钟的跨系统查询，1 分钟完成

**场景二：知识库问答 + 主动推送**
- 触发：定时任务 / 用户提问
- Agent 行为：调用智搜 MCP → LLM 摘要/问答 → 推送相关人员
- 价值：替代人工整理信息、替代人工回答重复性问题

**场景三：流程自动化（RPA 升级版）**
- 触发：用户指令 / 系统事件
- Agent 行为：操作内网 Web 系统（OA 审批、ERP 录入）→ 自动填表、提交
- 价值：替代重复性的人工操作，且能理解自然语言指令

**照读脚本：**

> 我们认为在南网场景下，有三个方向是最有落地价值的。第一个是"跨系统智能调度"——南网有大量的内部系统，告警系统、GIS、OA、ERP，现在这些系统之间的信息流转都需要人工来做。有了 Agent，运维人员只需要用自然语言说一句话，Agent 自动跨系统查询、整理、推送，效率提升是数量级的。第二个是"知识库问答 + 主动推送"，这个最容易落地，把智搜接进来，Agent 就能回答内部知识库的问题，还能定时主动推送相关信息。第三个是"流程自动化"，这个是 RPA 的升级版，Agent 能理解自然语言，不需要像传统 RPA 那样录制固定的操作步骤，更灵活、更智能。

| **数据源** | 公网搜索 | 内网智搜 / 企业知识库 |
| **推送渠道** | 微信/企业微信 | 钉钉 / 企业微信 / 内部 IM |
| **可审计性** | 有运行记录 | 完整 exec 审计日志 |
| **二次开发** | 不支持 | 完全开放，可深度定制 |

**照读脚本：**

> 我们来看一个非常具体的功能——定时任务。腾讯的 WorkBuddy 做了一个叫「自动化」的功能，大家可以看一下这几张截图。它的思路很简单：给 Agent 设置一个「闹钟」，到点自动执行一个任务，比如每天早上 9 点推送 AI 新闻，每周五汇总工作周报。用户只需要填三件事：任务名称、提示词、执行频率。这个功能非常直观，WorkBuddy 还内置了 7 个常用模板，普通用户开箱即用。
>
> 我们的方案能做同样的事，而且有几个关键优势。第一，**数据不出域**——WorkBuddy 是云端 SaaS，你的提示词、执行结果都在腾讯的服务器上；我们的方案部署在南网内网，所有数据留在自己手里。第二，**数据源是内部系统**——WorkBuddy 搜索的是公网，内网信息搜不到；我们接的是智搜和内部知识库，推送的是真正对南网员工有价值的内容。第三，**Cron 表达式更灵活**——WorkBuddy 只支持「每天固定时间」或「按小时间隔」，OpenClaw 支持标准 Cron 表达式，可以精确到秒，比如「每个工作日早上 8:30」「每月最后一个周五下午 4 点」这类复杂规则都能配置。第四，**完整审计日志**——每次定时任务的执行、调用了哪些工具、输出了什么，都有完整记录，满足电网的合规要求。

**照读脚本：**

> 定时任务在南网有哪些具体的落地场景？我们梳理了五个。第一个是「每日电网动态简报」，每天早上 8 点，Agent 自动从智搜抓取电力行业相关新闻，LLM 摘要后推送到管理层钉钉群，替代人工整理信息的工作。第二个是「告警日报汇总」，每天下班前，Agent 自动统计当天的告警情况，生成结构化日报，运维负责人不需要手动汇总。第三个是「每周运维周报」，这个更复杂一点，Agent 需要跨系统——告警系统、GIS、工单系统——汇总数据，然后用 LLM 分析趋势，生成周报。第四个是「合规检查提醒」，每月定期检查待审批工单、过期证书这类合规项，自动生成待办清单。第五个是「知识库更新推送」，内部知识库有新文档时，自动摘要推送给订阅了相关标签的员工。
>
> 这五个场景有一个共同特点：**它们都是现在已经在做的工作，只是在用人工完成**。定时任务的价值不是创造新工作，而是把这些重复性的信息整理和推送工作，从人工变成自动化。

## 第 14 页｜资源需求：通算还是智算？（直接回答客户问题二.1）

**页面标题（PPT 上显示）：**
> **OpenClaw 本身很轻，"重"的是模型推理**

**页面视觉内容（资源需求分层图）：**

**OpenClaw Gateway（通算）：**
- CPU：4 核即可（Gateway 是 Node.js 进程，轻量）
- 内存：8-16 GB
- 存储：100 GB（日志、会话状态、媒体缓存）
- 网络：内网互通即可

**模型推理层（智算，按场景选择）：**

| 场景 | 推荐方案 | 硬件需求 |
|------|---------|---------|
| 轻量问答/Skill 执行 | API 调用（通义/文心云端） | 无需本地 GPU |
| 中等复杂任务 | 私有化部署 7B-14B 模型 | 1-2 张 A100/H100 |
| 复杂推理/代码生成 | 私有化部署 70B+ 模型 | 4-8 张 A100/H100 |
| 完全离线（最高安全） | 量化模型本地推理 | 2-4 张 A100 |

**照读脚本：**

> 资源这块，我要帮大家拆开来看。OpenClaw 本身——也就是 Gateway 这个进程——非常轻量，4 核 CPU、16GB 内存就够了，这是纯通算资源。**真正消耗资源的是模型推理**。如果模型调用的是云端 API（比如通义千问的 API），那本地几乎不需要 GPU。如果要完全离线、不连任何外网，那就需要在内网部署推理服务，这时候才需要智算资源。我们建议南网分两步走：第一步先用云端 API 跑通业务场景，验证价值；第二步再根据实际需求评估是否需要私有化部署模型，以及需要多大规模的 GPU 资源。这样可以避免一开始就投入大量智算资源，但业务场景还没跑通的情况。

## 第 15 页｜Token 消耗控制：高频场景的应对策略（直接回答客户问题二.2）

**页面标题（PPT 上显示）：**
> **Token 不是越省越好，而是要"花在刀刃上"**

**页面视觉内容（四种策略卡片）：**

**策略一：上下文压缩（Compaction）**
- OpenClaw 内置自动压缩机制，长会话自动摘要历史，保留关键信息
- v2026.3.12 修复了压缩后 Token 计数异常的 Bug，压缩更精准

**策略二：Fast Mode（快速模式）**
- v2026.3.12 新增，对简单任务使用轻量模型（如 GPT-5.4 Spark），复杂任务才用重型模型
- 成本可降低 60-80%

**策略三：Skill 化高频任务**
- 将反复执行的任务固化为 Skill，减少 Agent 的"规划开销"
- 规划开销通常占总 Token 的 30-50%

**策略四：会话隔离 + 缓存**
- 不同任务使用独立会话，避免上下文污染
- 对重复性查询结果做缓存，相同问题不重复调用模型

**照读脚本：**

> Token 消耗这个问题，我们在做企业部署的时候经常遇到。有几个方法可以有效控制。第一个是 OpenClaw 内置的上下文压缩，长会话会自动摘要历史，不会无限累积 Token。第二个是 Fast Mode，这是 3.12 版本新加的功能，简单任务用小模型，复杂任务用大模型，成本能降 60-80%。第三个是最重要的——**把高频任务 Skill 化**。Agent 每次从头规划一个任务，要消耗大量 Token 在"想怎么做"上。但如果这个任务已经有 Skill，Agent 直接按剧本执行，规划开销几乎为零。所以对于南网这种有大量重复性任务的场景，Skill 化是控制成本最有效的手段。第四个是会话隔离和缓存，避免上下文污染，对重复查询做缓存。
